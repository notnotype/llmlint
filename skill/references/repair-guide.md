# 修复指导

本指南用于 Agent 生成修复计划和执行改写。它不是规则清单，而是修复时的动作纪律。

## 总原则

1. **删除优先**：先删空壳、铺垫、重复解释、抽象总结和无信息转场。只有删除会损失信息时才重写。
2. **具体优先**：把判断落到角色能看见、听见、触到或实际做出的动作上。
3. **少量修复**：每轮只处理最影响自然度、密度和可信度的问题，不追求把所有候选消成 0。
4. **保护声音**：对白、角色口癖、讽刺、文体模拟和题材设定可以保留。
5. **复测收敛**：修完只复测一轮；若仍有争议，报告剩余风险，不无限打磨。

## 三工序流水线

### 1. 删

判断删掉候选后信息是否几乎不变：

- 填充词、元叙述公告、空泛总结：通常直接删。
- 否定铺垫、二元反转：如果没有纠正真实误解，删前半句。
- 章尾预告腔：删掉替读者预告的句子，让事件停在动作、画面或台词上。

### 2. 压

删完仍显得断裂时，把必要信息压成短句：

- 把“这意味着/也就是说/关键在于”压成角色看到的结果。
- 把“命运/棋局/新的开始”压成当场的物理后果。
- 把动作清单合并，只保留推进情节或显露心理的动作。

### 3. 换

只有语义必须保留但旧句显机器味时才改写：

- 用主体 + 动作替代抽象名词行动。
- 用可观察反馈替代情绪说明。
- 用具体限制、选择或后果替代“意义重大/影响深远”。

## 对白分类

### 甲：角色声音，保留

角色口癖、反问、辩解、故意重复、身份设定内的技术/系统词，通常保留。例：台词里的“不是我干的，是他”不是叙述层二元对比。

### 乙：拿不准，交用户确认

如果一句话既像口癖又像模板，归乙。计划里说明两种判断，不直接改。

### 丙：叙述者借对白说说明书，修

如果对白只是替作者解释设定、公告规则或下结论，读起来不像角色在说话，应重写为角色当下反应、冲突或更自然的短句。

## 数据包腔例外

系统公告、面板、规则条文、技术说明可以保留“载体”。修复目标不是把它们改成散文，而是：

- 减少硬规则词堆叠。
- 把部分抽象处罚写成角色能理解的具体后果。
- 保留必要的术语和格式。
- 避免叙述者在系统面板外继续用 API 文档口吻解释。

## story-deslop 纪律

这些纪律来自 MIT 来源的 story-deslop 检测器设计，已重述为 llmlint 修复准则：

- **删除比例上限**：一轮修复不要大面积删到文意塌陷。若一段超过三分之一内容都想删，先停下，改为整体重写并说明原因。
- **删除优先于同义词替换**：套词密度、比喻密度、解释链过高时，不要把“仿佛”换成“宛如”，应减少这类结构总量。
- **收敛终止**：复测后若只剩风格性、人类可接受或需要上下文判断的问题，报告剩余风险并停止。
- **疑难上浮**：规则密集但检测热力低，优先怀疑误报；检测热力高但规则静默，记录为新规则候选，不强行套旧规则。

## 输出要求

修复计划应包含：

- 原文片段和行号。
- 修复/保留/确认三类结论。
- 简短理由。
- 拟改写文本。
- 本地 config 建议只以 diff 形式出现。

执行后报告：

- 修改了哪些类型的问题。
- 哪些候选保留，为什么。
- 复测结果。
- `.agent/llmlint-session.json` 是否已更新。
