# 修复指导

本指南用于 Agent 生成修复计划和执行改写。它不是规则清单，而是修复时的动作纪律。

## 总原则

1. **删除优先**：先删空壳、铺垫、重复解释、抽象总结和无信息转场。只有删除会损失信息时才重写。
2. **最小改动**：能删一个空壳就不重写一句，能改一句就不重写一段；人名、地名、数字、专名和章节结构优先保持原样。
3. **具体但不虚构**：优先使用原文已有的动作、物件、限制和后果。不能为了“展示而非告知”擅自补身体反应、感官细节或新事件。
4. **候选不是判决**：规则命中、密度指纹和 P(AI) 只提供审稿证据。每项都要结合上下文决定修、留或问。
5. **保护声音**：对白、角色口癖、讽刺、文体模拟和题材设定可以保留。
6. **复测收敛**：修完只复测一轮；若仍有争议，报告剩余风险，不无限打磨。复测判据是命中减少、无新命中、**篇幅在原文 ±20% 以内**三条同时成立。

## 判断顺序

每个候选按固定顺序处理：

1. 读取命中前后文，确认叙述视角、说话者和场景阶段。
2. 写清这句话承担的事实、因果、伏笔、人物声音、节奏或载体功能；说不清时先归入“问”。
3. 区分叙述、角色对白、作者借对白说明、系统/公告/数据包载体，不能用同一修法扫平。
4. 先决定 **修 / 留 / 问**，再选择 **删 / 压 / 换**；不能因为规则级别高就跳过功能判断。
5. 修改后对照原文，确认没有少掉必要信息，也没有增加原文不存在的情节、设定、关系、动机或时间线。

## 三工序流水线

### 1. 删

判断删掉候选后信息是否几乎不变：

- 填充词、元叙述公告、空泛总结：通常直接删。
- 否定铺垫、二元反转：如果没有纠正真实误解，删前半句。
- 章尾预告腔：删掉替读者预告的句子，让事件停在动作、画面或台词上。

### 2. 压

删完仍显得断裂时，把必要信息压成短句：

- 把“这意味着/也就是说/关键在于”压成原文已经呈现、角色能看到的结果。
- 把“命运/棋局/新的开始”压成原文已经发生的当场后果。
- 把动作清单合并，只保留推进情节或显露心理的动作。

### 3. 换

只有语义必须保留但旧句显机器味时才改写：

- 用主体 + 动作替代抽象名词行动。
- 用可观察反馈替代情绪说明。
- 用具体限制、选择或后果替代“意义重大/影响深远”。

只能使用原文已经给出的动作、物件、环境和后果。原文没有可用细节时，可以把抽象句压短或交用户确认，不能套用“手一抖、心口一沉、眼神一变”等库存反应来伪造具体感。

## 对白分类

### 甲：角色声音，保留

角色口癖、反问、辩解、故意重复、身份设定内的技术/系统词，通常保留。例：台词里的“不是我干的，是他”不是叙述层二元对比。

### 乙：拿不准，交用户确认

如果一句话既像口癖又像模板，归乙。计划里说明两种判断，不直接改。

### 丙：叙述者借对白说说明书，修

如果对白只是替作者解释设定、公告规则或下结论，读起来不像角色在说话，应重写为角色当下反应、冲突或更自然的短句。

## 数据包腔例外

系统公告、面板、规则条文、技术说明可以保留“载体”。修复目标不是把它们改成散文，而是：

- 减少硬规则词堆叠。
- 原文已经给出对应后果时，把部分抽象处罚写成角色能理解的具体后果；原文没给则保留或归入“问”。
- 保留必要的术语和格式。
- 避免叙述者在系统面板外继续用 API 文档口吻解释。

## 禁止机械去味

- 不把“仿佛”批量换成“宛如”，也不把一套陈词滥调换成另一套。
- 不把所有情绪都外化成身体微动作；低强度过场情绪可以直接写，关键是符合人物和场景。
- 不为制造“自然感”硬拆短句、删光连接词或把正文改成提纲/电报体。
- 不用统一段长、对话占比、标点数量或平台经验值压平原文节奏。
- 不为降低检测分数故意加错别字、随机口语、无关动作、感官细节或新情节。
- 不把载体内必要的术语、公文格式和规则句一律散文化。

## story-deslop 纪律

这些纪律来自 MIT 来源的 story-deslop 检测器设计，已重述为 llmlint 修复准则：

- **删除比例上限（段级 + 篇级）**：段级——若一段超过三分之一内容都想删，先停下，改为整体重写并说明原因。篇级——**全篇删减不超过两成**，用 `check` 报告的 `summary.visibleChars` 修复前后对比（与「/千字」同分母，别用 `wc`）。两个尺度都要看：只守段级挡不住「每段各删一点、全篇掉三分之一」，而这恰恰是实测出现过的形态（4663 → 3003 字，−35.6%），当时命中 55→2、`docPAi` 0.947→0.597，**两个指标都在变好，没有任何信号提示删多了**。接近或超过两成就报告给用户定夺。
- **删除优先于同义词替换**：套词密度、比喻密度、解释链过高时，不要把“仿佛”换成“宛如”，应减少这类结构总量。
- **剧情功能优先**：规则只能改变表达方式，不能删除伏笔、钩子、角色特征、人物记忆、情绪承接、因果锚点、关键信息或必要转折；冲突时改为降 AI 重写或交用户确认。
- **守住原文边界**：不新增原文没有的情节、设定、关系或时间线；原文逻辑问题不属于去 AI 味修复范围，应单独报告。
- **收敛终止**：复测后若只剩风格性、人类可接受或需要上下文判断的问题，报告剩余风险并停止。
- **疑难上浮**：规则密集但检测器给的文内位次低时，判为「规则与检测器分歧」，交人工裁决——**不要**直接推断为规则误报，检测器自己也会漏报（实测一段 `P(AI)=0.290` 的正文里 6 条命中经复核全部成立）。检测器位次高但规则静默时，记录为新规则候选，不强行套旧规则。
- **检测分数不是修复目标**：一轮修复后 `docPAi` 可能不降反升（实测 0.8757→0.8844，改动最集中的段落升 6 个百分点）。判断修得对不对看语义、角色声音、可读性和静态命中，不看检测分数是否下降。

## 输出要求

修复计划应包含：

- 原文片段和行号。
- 修 / 留 / 问三类结论。
- 简短理由。
- “修”项的拟改写文本；“留/问”项不伪造改写。
- 本地 config 建议只以 diff 形式出现。

执行后报告：

- 修改了哪些类型的问题。
- 哪些候选保留，为什么。
- 复测结果。
- `.agent/llmlint/session.json` 里本轮条目是否已填完。
